## Production deployment — live (2026-09-15/16), lessons for next time

Deployed to Vercel + a real Supabase project. Getting from "migrations ran, bootstrap ran" to "pages actually load data" took a full troubleshooting pass — worth recording precisely so it isn't rediscovered.

**Symptom:** every data-driven page (`/tasks`, `/capabilities`, `/budget`, etc.) showed "Couldn't load X — try refreshing" (or, on Budget specifically, a misleadingly clean "No services in this org yet" — see the bug entry below) even though migrations and bootstrap had both completed successfully and login worked.

**Root cause, found via a temporary `/api/debug` diagnostic endpoint (built, used, then deleted — see below) plus Vercel Runtime Logs:** `DATABASE_URL` was never set in Vercel's Production environment, so `lib/db-driver.ts` fell back to its local-dev default (`"file:./dev.db"`), routing every DB call through `node:sqlite` — which can't create/open a file on Vercel's read-only serverless filesystem (`ERR_SQLITE_ERROR: unable to open database file`, every route, identically). Supabase Auth env vars were present and correct the whole time (login worked), which is why this looked like a data-layer problem specifically, not an auth problem.

**The fix chain, in the order each issue actually surfaced (each one masked the next until fixed) — needed for every future deploy, not just this one:**

1. **Get the connection string from Supabase → Settings → Database → Connect → Connection string tab.** Supabase shows three connection methods here: Direct connection, Transaction pooler, Session pooler.
2. **Use the Transaction pooler string, not Direct connection.** Supabase's direct-connection hostname (`db.<ref>.supabase.co`) now resolves over IPv6 only — Vercel serverless functions have no IPv6 egress, so direct connection always fails with `getaddrinfo ENOTFOUND`. The pooler hostname (`aws-0-<region>.pooler.supabase.com:6543`) is IPv4-reachable and is what serverless functions are supposed to use anyway (short-lived connections, not persistent ones).
3. **Append `?sslmode=no-verify` to the connection string.** Without any `sslmode`, Postgres rejects the connection outright (`ESSLREQUIRED`). `sslmode=require` gets past that but then fails with `self-signed certificate in certificate chain` — Supabase's pooler cert isn't in Node's default trusted-CA path in this environment. `no-verify` keeps the connection encrypted while skipping chain validation, which is Supabase's own standard recommendation for pooler connections from serverless environments.
4. **Percent-encode special characters in the database password.** A literal `#` in the password breaks URL parsing outright (`#` starts a URL fragment, silently truncating everything after it) — encode it as `%23`. `!` is fine unencoded. When in doubt, either encode every non-alphanumeric character in the password or reset the password to alphanumeric-only via Supabase → Settings → Database → Reset database password, to remove the ambiguity entirely.
5. **Set the env var scoped to Production specifically**, not just Preview/Development, and **redeploy** after saving — env var changes don't apply to a deployment that's already built.

The working shape of the value:
```
postgresql://postgres.<project-ref>:<url-encoded-password>@aws-0-<region>.pooler.supabase.com:6543/postgres?sslmode=no-verify
```

## v3.0 roadmap — Phase 5: Document Generation Engine — done (2026-09-16)

Fifth phase of `vbp-navigator-os-v3-roadmap.md` (§8 completed — Phase 4 built the Engagement entity this phase generates documents against). All seven document types from the roadmap: proposal, quotation, invitation, approval request, confirmation, admission communication, completion record.

**The design call this phase turned on:** Customer/Engagement don't exist until a lead is admitted (Phase 4), but proposals/quotations/invitations/approval-requests conceptually need to go out *before* that. So documents anchor to whichever entity actually exists at that point in the relationship — a **Lead** for the four pre-admission types, an **Engagement** for the three post-admission types (confirmation, admission communication, completion record). `lib/document-templates.ts`'s `PRE_ADMISSION_TYPES`/`POST_ADMISSION_TYPES` sets are what decide which picker the UI shows and which the server requires.

- [x] **Schema** (`supabase/migrations/0013_phase5_documents.sql`) — one new `documents` table: anchored to `lead_id` or `engagement_id` (a check constraint requires at least one), `doc_type`, rendered `title`/`body`, the one free-text `details` field staff fill in per document, `status` (draft/pending_approval/approved/rejected), `version` + `previous_version_id` for the versioning model below, `sent_at`, and denormalized `created_by_name`/`approved_by_name` (same pattern as `tasks.assignee_name`/`service_requests.requester_name`). RLS: creating/regenerating needs that service's owner/contributor or an org admin (same bar as recording an Expense); approving/rejecting reuses `canApproveBudget` — the same real person (Anne) who approves Budget Requests and finalizes Compensation, not a new invented role.
- [x] **`lib/document-templates.ts`** (new) — seven pure template functions, code-defined (not a database-editable template system — nobody asked for a template editor). Body is plain text, blank-line-separated paragraphs, no markdown syntax — rendered with `white-space: pre-wrap` in the UI rather than through a markdown parser, so this didn't need a new dependency. Every field comes from real Service/Lead/Customer/Engagement/Org data except the one `details` field staff type themselves — nothing fabricated.
- [x] **`lib/document-context.ts`** (new) — the cross-module resolver: given a doc type and a lead-or-engagement id, pulls together service name/description/customer need, recipient name/email, and (for post-admission types) the engagement's start date. Shared by the create, regenerate, and new-version routes rather than duplicated across them.
- [x] **`lib/db-documents.ts`** (new) — persistence, same dual-driver pattern as every other `db-*.ts`. Small additions elsewhere to support it: `lib/db-engagements.ts` gained `getEngagement()` (single-row, alongside the existing list-shaped `listEngagements`), `lib/db-customers.ts` gained `getCustomerById()`, `lib/organizations.ts` gained `getOrgName()` (the reverse of the Phase 4 `getOrgBySlug`, needed so templates can write "offered by <org>" using a real name).
- [x] **Versioning model** — while `draft`, a document can be regenerated in place (same row, same version — `POST /api/documents/:id/regenerate`). Once `approved` (or `rejected`), it's immutable; changing it means `POST /api/documents/:id/new-version`, which opens a new row at `version + 1` with `previous_version_id` set, leaving the old row untouched as its own historical record. Verified this distinction is actually enforced, not just implied: regenerating an approved document is rejected server-side (see smoke test below).
- [x] **Approval flow** — one `PATCH /api/documents/:id` route handles all four status-transition actions (`submit`/`approve`/`reject`/`mark_sent`) rather than four separate routes, since they share the same "load it, check who's allowed, apply the transition" shape.
- [x] **`/documents`** (new, `components/documents/*`) — a "Generate a document" form (type picker swaps between a Lead picker and an Engagement picker depending on type), then Active/Closed-shaped lists (matching Pipeline/Prospects' visual pattern) — "Needs attention" (draft/pending_approval) and "Closed" (approved/rejected). Each document card: type/status badges, version, recipient, an expandable full-text view, and whichever actions its current status allows. Added "Documents" to `TopNav.tsx`.
